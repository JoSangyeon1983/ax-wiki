# 1 작업 정의

- 현재 요청에서 작성, 검토, 채택, 승인과 반영의 권한 범위 확인함. 읽기나 조사 요청을 채택 지시로 확대하지 않음.
- 결과물의 역할과 최종 목적 폴더 확인함. 기준은 [위키 작업 지침: 영역과 참조 범위](<../../AGENTS.md#4-영역과-참조-범위>)임.
- 기존 문서의 현재안, 대체안과 미확정 내용을 구분하고 변경 이유와 영향 대상을 확인함.

# 2 자료 선정

- 일반 문서의 출처는 최종 목적 폴더보다 앞번호인 자료에서 해당 작업에 확정되거나 채택된 범위만 선정함. 운영 색인과 로그는 기획 근거로 사용하지 않음.
- 기획에 참고 자료나 프로토타입 결과를 적용하려면 확인 가능한 채택 결정에 따라 `02_기획 근거`에 채택 내용, 적용 범위, 원자료 위치와 제외 사항을 먼저 정리함.
- 기획 근거에 연결된 원문은 채택된 범위의 대조에 사용함. 관련 자료를 연쇄적으로 탐색하거나 원문의 다른 내용까지 자동 적용하지 않음.
- 회의 내용은 반영된 프로젝트 회의록의 결정과 적용 범위를 확인함. 원본 대조와 회의록 작성은 [회의록 작성 규칙](<회의록 작성 규칙.md>) 적용함.

# 3 작성과 수정

## 3.1 작업 공간과 기획서

- 개인 초안, 아이디어와 대안 검토는 `90_작업 공간`에서 관리함. 작업명과 결과물 역할을 구분하고 [작성 규칙](<작성 규칙.md>)과 [문서 형식](<문서 형식.md>) 적용함.
- 회사 업무의 콘셉트 기획서는 `03_기반 기획`, 상세 기획서는 `04_상세 기획`에 작성 중 상태로 보관 가능함. 작성 주체와 위치만으로 승인 여부를 판단하지 않음.
- 상세 기획에는 승인된 콘셉트와 적용 기반 기획의 문서, 항목과 버전 기록함. 확인되지 않은 승인이나 새 조건은 미확인 또는 제안으로 구분함.
- 기존 확정 문서의 수정 전 상태와 승인된 콘셉트 버전은 파일 또는 Git 이력으로 보존함. 변경 영향과 요청 범위를 검토한 뒤 반영함.

## 3.2 구조와 검증 준비

- 정보 분류와 헤더 계층은 작성자와 Codex가 의미에 따라 결정함. 번호 도구가 계층을 임의 변경하지 않음.
- 작성이나 수정 후 헤더 번호를 적용하고 실제 수행한 검토 범위 기록함. 폴더 변경만으로 `status`를 확정 또는 승인 상태로 바꾸지 않음.

## 3.3 헤더 번호 도구 실행

### 3.3.1 실행 환경과 첫 번호 부여

- 실행 파일은 `00_시스템/03_도구/heading_numbers.py`, 환경은 Python 3.9 이상임. 별도 패키지 설치 없이 위키 루트에서 실행함.
- `type: article`인 기반 기획과 상세 기획 및 두 폴더를 목적지로 지정한 작업 공간 초안은 첫 문서 정보 절과 하위 헤더의 번호를 생략함. 첫 본문 H1은 `1`부터 시작함.

```powershell
python "00_시스템/03_도구/heading_numbers.py" apply "90_작업 공간/작업명/문서명.md" --input unnumbered
```

### 3.3.2 기존 번호 재계산과 제목 보존

- 이미 번호가 있는 파일은 `numbered` 사용함. 새 숫자 제목을 기존 번호로 오인하지 않도록 필요한 경우 실제 행 번호로 `--literal-line` 지정함.
- 기획서의 첫 문서 정보 절은 번호 적용에서 제외하고 본문 번호 재계산함. 과거 버전 이력의 당시 절 번호는 보존함.

```powershell
python "00_시스템/03_도구/heading_numbers.py" apply "03_기반 기획/콘셉트/문서명.md" --input numbered
```

### 3.3.3 적용 후 검사와 실행 범위

- `apply`는 명시한 파일만 수정함. `check`는 읽기 전용이며 경로 생략 시 보관소와 숨김 운영 영역을 제외한 전체 Markdown을 검사함.
- 위키 밖에서 실행할 때는 `--root`로 위키 루트 지정함. AGENTS.md 수정이 요청 범위에 없으면 해당 파일에 `apply`를 실행하지 않음.

```powershell
python "00_시스템/03_도구/heading_numbers.py" check
```

### 3.3.4 오류 처리와 인식 범위

- 계층이나 변경될 헤더의 링크 오류가 있으면 도구는 파일 수정 없이 중단함. 작성자가 의미와 실제 연결을 확인하고 재실행함.
- 인식 범위는 독립된 `#` 헤더와 일반 인라인 Markdown 및 Obsidian 헤더 링크임. 밑줄형 헤더와 추가 링크 문법은 별도 검토함.
- 파일과 이미지의 일반 경로도 확인함. 헤더 검사 통과를 기획 내용의 승인이나 출처 채택으로 취급하지 않음.

### 3.3.5 종료 상태와 도구 검증

- 종료 코드 `0`은 통과, `1`은 번호, 계층이나 링크 오류, `2`는 실행 조건 또는 파일 처리 오류임. 월별 로그는 `SKIP_LOG`로 표시함.
- 도구를 수정한 경우 동봉 검증 코드 실행함.

```powershell
python "00_시스템/03_도구/test_heading_numbers.py"
```

## 3.4 사용과 전달용 파일 작성

- 별도로 사용하는 엑셀, 문서, 발표 자료와 배포용 파일은 기본적으로 `08_산출물/작업명 또는 사용 목적명`에 작성하고 관리 기록을 함께 둠. 원본 지식 문서와 제작 자산 및 프로토타입 프로젝트의 위치는 해당 역할로 판단함.
- 입력 문서의 해당 항목과 기준 시점, 정본과 파생 출력의 관계, 변환 범위와 검토 상태를 기록함. 사용자 지정 범위의 서식 변환을 원문 내용의 채택이나 승인으로 취급하지 않음.
- 기존 출력 갱신 전 사용자 직접 수정과 정본 여부를 확인함. 파일 위치를 변경할 때 본문과 메타데이터 경로 및 기존 연결을 함께 갱신함.
- 생성, 갱신과 이동 시 [산출물 색인](<../00_색인/산출물 색인.md>)을 함께 수정함. 기존 위치의 자산과 검토용 구현은 복제하지 않고 색인에서 연결함.

# 4 검증

## 4.1 공통 검토

### 4.1.1 출처와 내용 상태

- 앞번호 출처 제한, 확정 또는 채택 범위와 실제 근거 위치를 대조함. 기준 후보나 이전 참고 연결을 출처 사용 허가로 취급하지 않음.
- 사실, 출처의 주장, 작성자의 해석과 미확정 사항 구분함. 임의 추가, 요청 누락, 기준 충돌과 미확정 내용의 혼입 확인함.
- 승인된 콘셉트의 항목과 버전, 상세 기획의 적용 위치와 변경 영향 검토함. 확인하지 않은 승인과 기준은 미확인으로 유지함.

### 4.1.2 서술과 문서 형식

- 분류, 용어, 설명 순서, 중복과 누락 및 개조식 표현 검토함. 프론트매터의 역할, 상태와 실제 위치가 일치하는지 확인함.
- 제목과 파일명, 번호와 헤더 계층, 링크, 이미지와 실행 경로를 확인함. 단어 사이 공백과 루트 폴더 번호 뒤 밑줄 규칙 준수함.
- 기획서 문서 정보는 번호 예외를 적용하고 월별 로그의 날짜와 시각 보존함. 번호 검사를 정보 구조의 의미 검토로 대체하지 않음.

### 4.1.3 자산과 재검증

- 자산의 열기 가능 여부, 파일 규격, 내용 보존과 실제 사용 위치 확인함. 이미지 생성과 검수는 [이미지 생성 규칙](<이미지 생성 규칙.md>) 적용함.
- 파일 정리 작업은 이동 전후 보존과 실제 경로 확인 범위를 기록함. 기존 시각 검수의 재사용과 새 시각 검수를 구분함.
- 기록이 있는 파일을 사용자가 옮겨 실물이 없으면 반환 경로를 준비하고 `반환 대기`로 기록함. 빈 대체 파일이나 재생성본을 만들지 않으며, 반환 후 실제 파일 대조 전까지 과거 검토를 현재 검증으로 보고하지 않음.
- 오류를 수정하면 영향 부분을 재확인함. 검수 보고에는 확인 범위, 문제, 판단 보류와 미확인 범위를 구분함.

## 4.2 프로토타입 실행과 구현 검토

- 실제 실행한 환경과 조건, 입력 근거, 핵심 동작과 관찰 결과를 대조함. 미실행 사유와 확인하지 못한 동작 기록함.
- 실행 성공을 기획의 승인이나 전체 품질 검증으로 취급하지 않음. 새 기획 적용은 별도 채택 범위로 판단함.

## 4.3 프로토타입 검증 기록

- 설명 문서에 실행 방법, 검증 대상과 조건, 결과와 한계 기록함. 동봉 자산의 원본 출처와 경로 확인함.
- 프로토타입 결과를 기획서에 직접 역참조하지 않음. 채택 결정이 있으면 필요한 내용과 범위만 `02_기획 근거`에 먼저 반영함.

# 5 확정과 반영

## 5.1 반영 대상과 상태

- 확정과 반영은 요청에서 부여된 권한 범위대로 수행함. 회사 업무의 미승인 기획서가 기획 폴더에 있다는 이유로 자동 확정하지 않음.
- 개인 초안이나 검토 제안은 작업 공간에 유지함. 프로젝트 기록, 참고 자료, 자산과 프로토타입도 역할과 실제 검증 및 채택 상태를 기록함.
- `confirmed`와 회사의 콘셉트 승인을 구분함. 사용자 버전 값을 임의 부여하거나 증가시키지 않음.

## 5.2 이동과 색인

- 실제 내용과 역할로 개별 분류함. 참고 자료를 기획 근거로 일괄 승격하지 않으며 파일 이동만으로 상태를 높이지 않음.
- 정식 반영 시 목적 폴더가 확정된 문서의 `target_folder`를 제거함. 작성일은 보존하고 변경된 내용과 검토 범위에 맞게 수정일과 기록 갱신함.
- 관련 규정, 색인, 본문과 메타데이터 링크, 도구 경로 및 `.gitignore` 함께 확인함. 실제 보관 내용이 있는 하위 폴더만 생성함.
- 대체된 기획, 종료된 작업과 미채택 자료는 `99_보관소`에서 로컬 보관함. Git 추적 제외와 외부 영역에서 내부로 연결하는 링크 금지 유지함. 보관 이유와 대체 위치 기록함.

## 5.3 프로토타입 반영

- 요청 범위에 정식 반영이 포함되면 프로젝트와 설명 및 검증 기록을 `07_프로토타입/검증 대상명`에 함께 반영함.
- 실제 검증 범위, 의존성, 실행 경로와 동봉 자산 출처를 점검함. 확인하지 않은 내용은 미확인 상태로 유지함.

## 5.4 산출물 반영과 반환 준비

- 사용과 전달용 파일 및 관리 기록을 `08_산출물`에 함께 반영하고 산출물 색인에서 연결함. 파일 보관 위치와 문서의 검토 또는 승인 상태는 구분함.
- 사용자 이동 파일의 반환 예정 경로, 이전 기록 위치와 현재 실물 부재를 기록함. 반환 대기 파일은 자동으로 재생성하지 않으며, 예정 경로에 파일을 놓은 뒤 존재와 열기 가능 여부 및 기록 일치 범위를 다시 확인함.
- 보관된 이전 출력은 현재 산출물과 별도로 목록화하고 보관 상태를 유지함. 반환 목록의 보관소 경로는 링크가 아닌 일반 텍스트로 표시함.

# 6 월별 로그

## 6.1 기록 범위

- 실제 위키 파일 변경이 있는 작업을 `00_시스템/02_작업 기록/YYYY-MM.md`에 기록함. 여러 파일을 변경한 작업은 한 항목으로 묶음.
- 로그 기록 자체를 별도 작업으로 재기록하지 않음. 해당 월의 문서가 없으면 실제 작업 달의 로그 생성함.

## 6.2 날짜와 항목 형식

- 한국 표준시(Asia/Seoul)의 실제 날짜와 시각 사용함. 시간이 불명확하면 날짜만 기록함.
- 각 항목은 날짜, 시각과 작업명인 H1으로 식별하고 H1~H5의 번호 적용은 제외함.

## 6.3 삽입과 정렬

- 새 항목은 프론트매터 다음에 삽입하고 시각의 내림차순으로 배치함. 기존 항목에 번호를 다시 부여하지 않음.
- 과거 기록의 당시 경로, 버전과 수행 결과는 보존함. 경로 변경 내용은 새 작업 항목에 기록함.

## 6.4 기록 내용과 색인

- 대상, 작업, 이유, 검증, 결과를 [문서 형식: System과 Logs](<문서 형식.md#10-system과-logs>)에 따라 작성함.
- 로그는 운영 이력이며 기획 내용의 근거가 아님. 새 월별 로그와 실제 역할별 문서를 색인에 연결함.
