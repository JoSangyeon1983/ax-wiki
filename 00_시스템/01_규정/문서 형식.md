# 1 기본 형식

- 문서는 UTF-8(8-bit Unicode Transformation Format) Markdown으로 저장.
- `AGENTS.md`를 포함한 관리, 지식, 리소스 설명, 프로토타입 설명, 로그 문서는 파일 최상단에 YAML(YAML Ain't Markup Language) 프론트매터 배치.
- 문서 제목은 프론트매터의 `title`에서 관리. 1단계 헤더(H1, Heading 1)는 본문의 대분류로 사용. 기획서의 첫 `문서 정보` H1은 관리 정보 표시용 예외이며 [기획서 문서 정보의 번호 예외](<#33-기획서-문서-정보의-번호-예외>) 준수.
- 아래 본문 항목은 기본 구성. 문서 목적에 맞게 항목명과 상세 수준 조정 가능.
- 예시의 `문서 제목`, `문서명`, `작성일` 등은 실제 값으로 대체. 확인된 출처가 없는 경우 `sources: []` 유지와 사유의 본문 기록.

# 2 문서 제목과 파일명

- `title`은 문서 제목, 파일명은 파일 저장과 식별을 위한 이름. 서로 별개의 항목이며 `title` 수정 시에도 파일명은 자동으로 변경되지 않음.
- 일반 지식 문서, 리소스 설명 문서와 프로토타입 설명 문서는 기본적으로 파일명의 확장자를 제외한 이름과 `title` 일치. 예: `전투 시스템.md`의 `title`은 `전투 시스템`.
- 고정 이름을 사용하는 운영 문서와 월별 로그는 예외. 예: `AGENTS.md`의 `title`은 `위키 작업 지침`, `2026-10.md`의 `title`은 `2026년 10월 작업 로그`.
- 도구가 인식하는 `AGENTS.md`와 기존 자동화 스크립트의 파일명 유지. 그 밖의 폴더와 문서의 단어 사이는 공백 사용. 파일명 변경 시 해당 파일을 가리키는 링크도 함께 갱신.
- 문서 제목의 본문 H1 중복 표기 없이 첫 대분류부터 본문 시작.

# 3 헤더 넘버링

## 3.1 번호 형식

| 레벨 | 번호 형식 | Markdown 예시 |
|---|---|---|
| H1 | `1`, `2`, `3` | `# 1 대분류` |
| H2(Heading 2) | `1.1`, `1.2`, `1.3` | `## 1.1 중분류` |
| H3(Heading 3) | `1.1.1`, `1.1.2`, `1.1.3` | `### 1.1.1 소분류` |
| H4(Heading 4) | `1)`, `2)`, `3)` | `#### 1) 세부 항목` |
| H5(Heading 5) | `(1)`, `(2)`, `(3)` | `##### (1) 상세 항목` |

- 번호와 헤더 제목 사이에 공백 하나 배치.
- H1 번호 끝에는 마침표를 붙이지 않음. 예: `# 1 개요`.
- 헤더 레벨의 건너뜀 없이 정보 계층에 맞게 사용.
- 헤더 번호와 본문의 번호 목록은 서로 독립적으로 관리.

## 3.2 번호 초기화와 갱신

### 3.2.1 레벨별 번호 부여

- 번호 적용 대상 H1은 문서 본문 순서대로 `1`부터 연속 부여. 기획서의 첫 문서 정보 절은 [번호 예외](<#33-기획서-문서-정보의-번호-예외>)에 따라 제외.
- H2는 H1 번호에 해당 H1 안의 순번 추가. H1 변경 시 마지막 순번은 `1`부터 재시작.
- H3는 H2 번호에 해당 H2 안의 순번 추가. H2 변경 시 마지막 순번은 `1`부터 재시작.
- H4는 각 H3 안에서 `1)`부터, H5는 각 H4 안에서 `(1)`부터 재시작.

### 3.2.2 절 변경과 참조

- 절 추가, 삭제, 이동 시 해당 문서의 번호 갱신. 변경된 헤더를 가리키는 링크도 점검.
- 특정 절 참조 시 문서명과 헤더 제목 병기. 세부 참조 방식은 [작성 규칙: 근거와 판단의 표시](<작성 규칙.md#5-근거와-판단의-표시>) 준수.
- 변경 이력 표의 과거 절 번호는 당시 기록으로 보존. 현재 절 번호로 일괄 치환 금지.

## 3.3 기획서 문서 정보의 번호 예외

- 적용 대상: `type: article`인 `03_기반 기획`과 `04_상세 기획` 하위 기획서 및 두 폴더 중 하나를 `target_folder`로 지정한 `90_작업 공간` 기획서 초안.
- 문서 정보가 있는 경우 첫 H1을 `# 문서 정보`로 표기. `0`을 포함한 번호 생략.
- 문서 정보 절의 하위 헤더도 번호 생략. 다음 H1 직전까지 번호 계산에서 제외하며 헤더 계층과 링크 검사는 유지.
- 첫 본문 H1부터 `1`로 시작. H2 이하에는 기존 번호 형식 적용.
- 문서 정보가 없는 경우 첫 본문 H1부터 `1`로 시작. 형식 통일을 위한 빈 문서 정보 절 추가 불필요.

# 4 프론트매터

| 필드 | 적용 | 값과 의미 |
|---|---|---|
| `title` | 공통 필수 | 문서 제목 문자열 |
| `type` | 공통 필수 | `system`, `reference`, `synthesis`, `article`, `asset`, `prototype`, `log` 중 하나 |
| `created` | 공통 필수 | 최초 작성일. `"YYYY-MM-DD"` 문자열 |
| `updated` | 공통 필수 | 마지막 내용 수정일. `"YYYY-MM-DD"` 문자열 |
| `status` | 지식, 리소스 설명, 프로토타입 설명 문서 필수 | `draft`, `review`, `confirmed`, `superseded`, `rejected` 중 하나 |
| `sources` | 지식, 리소스 설명, 프로토타입 설명 문서 필수 | 실제 사용한 근거 문서와 원자료 목록 |
| `source_check` | `reference` 문서 필수 | `unverified`, `partial`, `verified`, `not_applicable` 중 하나 |
| `reviewed` | 확정 기획서, 자산, 프로토타입 필수 | 마지막 검토일. `"YYYY-MM-DD"` 문자열 |
| `review_note` | 확정 기획서, 자산, 프로토타입 필수 | 실제 수행한 검토와 남은 한계의 간단한 기록 |
| `target_folder` | 정식 폴더 반영을 준비하는 작업 공간 문서 필수 | 최종 목적 폴더. `01_프로젝트`, `02_기획 근거`, `03_기반 기획`, `04_상세 기획`, `05_참고 자료`, `06_자산`, `07_프로토타입`, `08_산출물` 중 하나 |
| `planning_role` | 기획서 필수 | `foundation`은 기반 기획, `detail`은 상세 기획 |
| `approval_status` | 기획서 필수 | `unverified`, `pending`, `approved`. 승인 근거가 확인된 경우에만 `approved` 사용 |
| `related_documents` | 필요 시 | 이전 참고 자료, 기준 후보와 영향 검토용 연결. 출처 사용 허가를 의미하지 않음 |
| `asset_files` | 리소스 설명 문서 필수 | 해당 설명 문서가 관리하는 파일의 위키 루트 기준 경로 목록. 실물이 없으면 본문에 상태와 반환 예정 경로 명시 |

## 4.1 출처 기록

- `sources`의 내부 문서 링크는 위키 루트 기준 Obsidian 링크 문자열로 기록. 예: `"[[01_프로젝트/과제 요구사항/문서명]]"`.
- 외부 원자료는 URL 또는 식별 가능한 서지 정보 기록. 페이지, 절, 시점 등 세부 근거 위치는 본문에 기록.
- `sources`에 운영 규정이나 작업 로그 포함 금지. `target_folder`의 허용 범위는 루트의 [위키 작업 지침: 기획과 산출물의 출처 제한](<../../AGENTS.md#42-기획과-산출물의-출처-제한>) 준수.

- 원본 동봉 파일, 기획 근거의 원문 추적, 회의 원본 검증, 표시와 변환의 용도별 예외는 같은 지침의 연결 용도별 적용 범위 표를 따름. 위치 안내와 기획 기준으로의 채택을 구분함.

## 4.2 상태와 대조 범위

- `status`는 문서의 작업과 채택 상태. `confirmed`는 모든 출처의 사실 입증이나 회사의 콘셉트 승인을 의미하지 않음. 기획서의 승인 여부는 확인 가능한 승인 기록으로 구분함.
- `source_check`는 원자료 대조 상태. `verified`도 원자료 자체의 완전한 진실성을 보증하지 않음. 확인 방법과 범위는 본문에 기록.
- 원자료 미대조 시 `unverified`, 일부 대조 시 `partial`, 해당 범위 대조 완료 시 `verified`로 기록. 외부 사실 검증 대상이 아닌 사용자 요구사항 등은 사유와 함께 `not_applicable`로 기록 가능.
- `superseded`는 다른 내용으로 대체된 문서, `rejected`는 채택하지 않은 작업물. 현재 확정 내용과의 혼합 방지를 위해 대체 위치나 사유를 본문에 표시.

# 5 프로젝트 기록과 참고 자료

```yaml
---
title: "문서 제목"
type: reference
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
status: draft
sources: []
source_check: unverified
---
```

- 과제 원본과 공식 기록은 `01_프로젝트`, 조사 원문과 일반 참고 자료는 `05_참고 자료`에 보관함. 수집과 보관을 기획 적용 결정으로 취급하지 않음.
- 기본 본문: `자료 개요`, `출처와 작성 방식`, `내용`, `확인 범위와 미확인 사항`. 프로젝트 회의록은 [회의록 작성 규칙](<회의록 작성 규칙.md>) 적용함.
- `sources`에는 실제 사용한 외부 원자료나 사용자 제공 원본의 식별 정보를 기록함. 프로젝트 기록 안의 관련 문서 연결은 원문 대조와 영향 확인을 위한 것으로 구분함.
- 대규모 언어 모델(LLM, Large Language Model)의 작성 설명을 외부 사실 입증 자료로 취급하지 않음. 원자료 연결과 미확인 범위를 구분함.

# 6 기획 근거와 참고용 분석

```yaml
---
title: "기획 근거 제목"
type: synthesis
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
status: review
sources: []
---
```

- `02_기획 근거`에는 기획에 사용하기로 정한 정보와 조건만 정리함. 기본 본문: `채택 내용`, `적용 범위`, `원자료와 위치`, `채택 근거`, `제외 사항과 한계`.
- 사용자 명시적 반영 지시 또는 확인 가능한 결정 기록에서 채택 근거를 확인함. 원자료 전체 복사나 이동으로 채택 절차를 대체하지 않음.
- 참고 자료와 프로토타입을 채택 내용의 원문 대조에 연결하는 경우 [위키 작업 지침: 자료 검토와 기획 근거 반영](<../../AGENTS.md#43-자료-검토와-기획-근거-반영>)에 따른 추적용 출처임. 원문의 다른 내용을 기획에 자동 적용하지 않음.
- 미채택 분석과 적용 제안은 `90_작업 공간`, 참고용 분석은 `05_참고 자료/분석 자료`에 보관함. 참고용 분석의 기본 본문은 목적과 범위, 분석, 해석과 추론, 한계로 구성함.

# 7 기반 기획과 상세 기획

```yaml
---
title: "기획서 제목"
type: article
planning_role: foundation
approval_status: unverified
created: "YYYY-MM-DD"
updated: "YYYY-MM-DD"
status: draft
sources: []
---
```

## 7.1 역할과 위치

- `03_기반 기획`은 상세 기획의 방향, 조건과 공통 규칙을 정의함. 콘셉트, 디바이스와 공통 규칙은 실제 문서가 있을 때 하위 폴더로 구분함.
- `04_상세 기획`은 적용 가능한 기반 기획을 구체화함. `planning_role: detail`로 기록하고 실제 기획 대상명으로 폴더 구성함.
- 작성 중인 회사 업무 기획서도 해당 기획 폴더에 보관 가능함. 사람과 AI의 작성 여부나 파일 위치만으로 승인 상태를 판단하지 않음.
- 기본 본문은 목적과 범위, 기획 본문, 한계와 미정 사항, 적용 기준으로 구성함. 기존 문서의 목적에 맞게 항목 조정 가능함.

## 7.2 출처와 기준 문서

- 일반 출처는 최종 목적 폴더보다 앞번호의 자료에서 해당 작업에 확정되거나 채택된 범위만 사용함. 같은 번호나 뒷번호 문서를 근거로 사용하지 않음.
- 기획서에서 `05_참고 자료`, `07_프로토타입`, `08_산출물`, `90_작업 공간`, `99_보관소`를 직접 기획 근거로 사용하지 않음. 자산의 표시용 첨부와 초안 편집은 근거 사용과 구분함.
- 상세 기획에는 승인된 콘셉트와 적용하는 기반 기획의 문서, 항목, 버전과 승인 범위 기록함. 승인이 확인되지 않은 연결은 기준 후보와 미확인 상태로 표시함.
- `related_documents`는 과거 참고와 변경 영향 확인용 연결임. 승인이나 채택이 확인되기 전에 `sources`나 적용 기준으로 바꾸지 않음.

## 7.3 문서 정보와 변경 관리

- 문서 정보가 있는 경우 본문 앞에 배치하고 [기획서 문서 정보의 번호 예외](<#33-기획서-문서-정보의-번호-예외>) 적용함.
- 버전 번호와 버전 변경 이력 행은 사용자가 명시한 값과 지시에 따라 반영함. Codex의 작업은 월별 작업 기록에 남김.
- 확정 기획서의 `reviewed`와 `review_note`에는 실제 검토 범위와 한계 기록함. 승인된 콘셉트는 파일 또는 Git 이력으로 식별 가능하게 보존하고 개정안 승인 전 상세 기획의 기준을 자동 교체하지 않음.

# 8 자산

## 8.1 관리 단위

- 제작하거나 가공한 이미지, 영상, 음원과 도표는 `06_자산`에서 관리함. 실제 보관할 내용이 있을 때 해당 하위 폴더 생성함.
- 바이너리에는 프론트매터를 삽입하지 않고 `type: asset`인 Markdown 설명 문서를 함께 관리함. `asset_files`에는 위키 루트 기준 실제 파일 경로 기록함.
- 이미지 여러 장은 콘텐츠별 통합 작업 기록 1개로 관리 가능함. 사용자가 기록의 별도 위치를 지정한 경우 작업 공간에 유지할 수 있음.
- 기본 본문: 용도, 파일과 규격, 입력과 생성 또는 편집 방법, 검토 결과와 한계. 확정 자산은 `reviewed`, `review_note` 기록함.

## 8.2 이미지 삽입과 링크 경로

- 이미지 삽입은 HTML `<img>` 방식만 사용함. `<img src="상대 경로/이미지 이름.png">`처럼 경로를 큰따옴표로 감싸고 공백 유지함.
- 기존 원자료와 사용자 편집 본문 안의 Markdown 이미지 문법은 원형 보존 가능함. 새로 작성하는 설명과 삽입에는 위 HTML 방식을 적용하며 실물이 없는 이미지는 결손 상태를 함께 기록함.
- 본문 링크는 현재 문서에서 대상 파일까지의 상대 경로, `sources`와 `asset_files`는 위키 루트 기준 경로 사용함.
- 생성과 검수 및 중간 자료 관리는 [이미지 생성 규칙: 최종 이미지와 통합 작업 기록](<이미지 생성 규칙.md#54-최종-이미지와-통합-작업-기록>) 준수함.

# 9 프로토타입

- `07_프로토타입`의 실제 검증 대상명 하위에 프로젝트 파일, 설명용 Markdown과 검증 기록 함께 관리함. 소스 코드에 프론트매터를 삽입하지 않음.
- 설명 문서는 `type: prototype`, 제목, 작성일과 수정일, 상태와 실제 입력 출처를 기록함. 기본 본문은 목적, 입력 근거, 실행 방법, 검토 결과, 한계임.
- 개인 구현 초안은 `90_작업 공간`에서 작업하고 정식 반영 대상이면 `target_folder: 07_프로토타입` 기록함.
- 실행 결과에는 검증 대상과 조건, 관찰한 동작, 미실행 범위와 남은 한계 기록함. 확정 시 `reviewed`, `review_note` 추가함.
- 프로토타입 결과의 기획 적용은 별도 채택 결정에 따라 `02_기획 근거`에 필요한 내용과 범위를 정리한 뒤 수행함.

# 10 System과 Logs

- 시스템 문서는 `type: system`과 공통 필드 4개 및 실제 운영 내용 기록함. 시스템 하위 폴더는 다음 역할로 구분함.

| 하위 폴더 | 관리 대상 |
|---|---|
| `00_시스템/00_색인` | 위키 색인과 탐색 안내 |
| `00_시스템/01_규정` | 작성, 형식, 작업 절차와 작업별 운영 규정 |
| `00_시스템/02_작업 기록` | 월별 작업 로그 |
| `00_시스템/03_도구` | 운영 및 검증 도구와 동봉 검증 코드 |

- 월별 로그는 `00_시스템/02_작업 기록/YYYY-MM.md`에 `type: log`로 작성함. 새 기록은 프론트매터 다음에 최신 시각부터 배치함.
- 항목은 실제 한국 표준시의 날짜, 시각과 작업명으로 식별하며 번호를 적용하지 않음. 대상, 작업, 이유, 검증, 결과의 5개 항목 기록함.
- 실제 파일 변경이 있는 작업만 기록함. 과거 로그의 당시 경로와 버전은 역사적 기록으로 보존하고 새 구조의 현재 연결과 구분함.

# 11 작업 공간과 파일 이동

- 개인 초안, 아이디어, 대안 검토와 피드백 반영 작업은 실제 작업명으로 `90_작업 공간`에 보관함. 정식 반영을 준비하는 문서에는 해당 종류와 `target_folder` 기록함.
- 작업 공간에 계속 보관할 운영 또는 작업 기록은 `type: system`과 공통 필드 사용함. 정식 반영 예정이 없는 기록에 임의 목적 폴더를 지정하지 않음.
- 파일 이동은 역할과 실제 상태를 기준으로 수행함. 폴더 이동만으로 확정이나 승인 상태를 올리지 않음. 링크, 출처와 실행 경로 및 필요한 영향 기록 갱신함.
- `99_보관소`는 Git 추적 제외를 유지함. 보관 이유와 대체 위치를 기록하고 보관소 밖에서 내부 파일이나 폴더로 연결하는 링크를 만들지 않음.

# 12 산출물

## 12.1 관리 단위와 형식

- 위키를 이용해 별도로 만든 사용, 전달과 발표용 파일은 `08_산출물/작업명 또는 사용 목적명`에 저장함. 확장자별 공통 폴더보다 함께 사용하는 작업 단위로 구성함.
- 바이너리에는 프론트매터를 삽입하지 않고 `type: asset`인 설명 문서를 함께 관리함. 기존 `status`, `sources`, `asset_files`와 확정 시의 검토 필드 적용함.
- 기본 본문은 용도와 파일, 정본과 입력 범위, 작성 또는 변환 방법, 검토 결과와 한계, 현재 파일 상태로 구성함. 여러 파일의 용도와 생성 기준이 같으면 하나의 기록으로 관리 가능함.
- 원본 지식 문서, 재사용할 제작 자산, 프로토타입 프로젝트와 중간 작업물은 기존 역할별 위치에서 관리함. 산출물 색인에 연결하여 한곳에서 접근하게 함.

## 12.2 정본과 갱신 기준

- 설명 문서에 내용을 수정하는 정본과 파생 출력물의 관계 기록함. 원본의 해당 항목, 파일 또는 Git 기준 시점과 실제 사용한 입력 범위 명시함.
- 서식 변환은 원문의 검토, 채택과 승인 상태를 유지함. 사용자가 지정한 앞번호 문서의 변환 범위만 입력으로 사용하며 새 해석이나 미승인 내용을 확정 사항으로 추가하지 않음.
- 재출력 전에 사용자가 출력 파일을 직접 수정했는지와 기존 파일의 정본 여부 확인함. 확인 없이 사용자의 변경을 덮어쓰지 않음.
- 최신 파일과 이전 출력의 관계를 기록하고 버전 값은 사용자 지시에 따름. 파일 존재 여부와 검토 또는 승인 상태를 별개로 표시함.

## 12.3 색인과 반환 대기

- [산출물 색인](<../00_색인/산출물 색인.md>)에 용도, 실제 파일 위치, 원본 또는 관리 기록, 검토 상태와 파일 상태 기록함. 생성, 갱신과 이동 시 함께 수정함.
- 사용자 이동으로 실물이 없는 파일은 `반환 대기`로 표시하고 `asset_files`와 본문에 반환 예정 경로를 기록함. 없는 파일로 연결하는 열기 링크 대신 경로를 일반 텍스트나 코드로 표시함.
- 반환할 폴더에 관리 기록을 준비하고 빈 파일이나 임의 재생성본은 만들지 않음. 이전 검토 결과는 당시 날짜와 범위를 보존하며 현재 실물 검증 완료로 표시하지 않음.
- 파일 반환 후 존재와 열기 가능 여부 및 기록과의 일치를 확인하고 색인과 관리 기록 갱신함. 보관된 이전 출력은 보관 상태를 유지하며 보관소 밖에서 내부로 연결하는 링크를 만들지 않음.
